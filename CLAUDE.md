# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Gitnuro is a desktop Git client written in Kotlin/JVM with Compose Multiplatform (Desktop) for the UI and JGit for Git operations. A small Rust library (`rs/`) handles file watching and LibSSH-based SSH.

## Build & run

Requirements: JDK 25 (the Gradle toolchain is pinned to 25 in `buildSrc` and `app/build.gradle.kts`; `DEVELOPMENT.md` still says 17, which is outdated), `cargo`/`rustc` on PATH, and Perl (for the vendored OpenSSL build; on Windows it must be a native Perl such as Strawberry Perl, Git Bash's Perl is rejected by OpenSSL's `Configure`).

The Gradle daemon itself must run on a HotSpot JDK 25: OpenJ9 builds (e.g. IBM Semeru) make KSP fail with "Flight Recorder is not supported on this VM", and a JDK below 25 can't load `buildSrc`. If `~/.gradle/gradle.properties` sets `org.gradle.java.home` to another JDK, override it per command:

```bash
./gradlew :domain:test :data:test "-Dorg.gradle.java.home=C:\Program Files\Eclipse Adoptium\jdk-25.0.4.101-hotspot"
```

```bash
./gradlew run                     # run the app (pass a repository path with --args="<path>" to open it)
./gradlew build                   # full build (what CI runs)
./gradlew test                    # all tests (JUnit 5 + MockK)
./gradlew :domain:test :data:test # tests only, without the Rust build
./gradlew :data:test --tests "com.hugodehu.gitmiro.data.git.workspace.ResolveConflictWithSideGitActionTest"   # single test class
./gradlew rustTasks               # build Rust lib, copy it into app resources, regenerate Kotlin bindings
./gradlew fatJarLinux             # portable Linux JAR (-PisLinuxAarch64=true -PuseCross=true for ARM)
./gradlew createDistributable     # native distribution (Windows/macOS)
```

`createDistributable` embeds a Java runtime with `includeAllModules = true`, so it must run on a JDK that ships `jmods` (e.g. the JetBrains Runtime SDK `jbrsdk`, as in CI). Temurin 25 doesn't ship them and `jlink` fails with "This JDK does not contain packaged modules". The Windows installer is then built from the distributable with Inno Setup: `iscc /DMyAppVersion=1.0.0 gitnuro.iss` writes `Output/GitMiro_Windows_Installer_1.0.0.exe` (per-user install, no admin rights needed). When releasing, bump `projectVersion`/`projectVersionSimplified` in `app/build.gradle.kts` and `APP_VERSION`/`APP_VERSION_CODE` in `AppConstants` together. Update checks are disabled while `AppConstants.VERSION_CHECK_URL` is null.

Tests live in `domain/src/test/kotlin` (pure model logic) and `data/src/test/kotlin` (Git actions). Git action tests run against real temporary repositories (`@TempDir` + `Git.init()`), build `JGit { WindowsFs(ShellManager()) }` directly instead of going through Dagger, and set `core.autocrlf=false` on the test repo so results don't depend on the machine's global Git config. Only `:app:compileKotlin` triggers the Rust build, so `:domain:test` and `:data:test` run without `cargo` (they still need the generated bindings from a previous `rustTasks` run).

`compileKotlin` in `:app` depends on `rustTasks`, so every app compile runs `cargo build`. That task:
1. builds `rs/` (release by default; `-PisRustRelease=false` for debug),
2. copies `gitnuro_rs.dll` / `libgitnuro_rs.so` / `.dylib` into `app/src/main/resources` (gitignored),
3. builds `rs/` again in debug and runs its `uniffi-bindgen` binary to generate Kotlin bindings into `domain/src/main/kotlin/com/hugodehu/gitmiro/autogenerated/` (gitignored, wiped on each run).

Don't edit the generated bindings; change `rs/src/lib.rs` (`#[uniffi::export]` items) instead.

The app version lives in two places that must stay in sync: `projectVersion` in `app/build.gradle.kts` and `AppConstants.APP_VERSION` (+ `APP_VERSION_CODE`).

## Architecture

Gradle modules (`settings.gradle.kts`), all applying the `buildsrc.convention.kotlin-jvm` convention plugin (enables `-Xexplicit-backing-fields` and `-Xcontext-parameters`):

- **`common`** – tiny shared utilities and the `@TabScope` Dagger scope.
- **`domain`** – models, use cases (`domain/usecases`), and interfaces for Git operations (`domain/interfaces/I*GitAction`), repositories and services. Also holds the Rust bindings and LibSSH glue.
- **`data`** – implementations: JGit-backed `*GitAction` classes grouped by feature under `data/git/*`, repository/settings implementations (DataStore), mappers from JGit types to domain models.
- **`app`** – entry point (`main.kt` → `App.kt`), Compose UI (`ui/`), ViewModels, theme, keybindings, and all Dagger wiring (`di/`).
- **`ui`** – empty placeholder module.

The code is mid-refactor toward this layering: `domain` and `app` still depend directly on JGit/Compose (marked `TODO Remove after refactor`), so expect some JGit usage outside `data`.

### Request flow for a Git operation

ViewModel → `XxxUseCase` (domain) → `IXxxGitAction` (domain interface) → `XxxGitAction` (data, JGit). Git actions are `suspend operator fun invoke(repositoryPath, ...)` returning `Either<T, GitError>`.

Use cases run their work through `UseCaseExecutor` (`domain/UseCaseExecutor.kt`), which supplies the current repository path, tracks a `TaskType` for progress UI, handles errors, and then triggers a refresh of the parts of state listed in `dataToRefresh` (`DataToRefresh` enum in `RefreshDataUseCase.kt`: `ALL`, `BRANCHES`, `LOG`, `STATUS`, `STASHES`, ...). When adding an operation, pick the narrowest refresh set that covers what it changes.

### Dependency injection (Dagger 2 via KSP)

- `AppComponent` (`@Singleton`) – app-wide modules (shell, network, credentials, settings/DataStore, services).
- `TabComponent` (`@TabScope` subcomponent) – one per open repository tab. Each tab has its own git actions, repositories and file watcher, so per-repo state lives here.

Adding a new Git action means: interface in `domain/interfaces`, implementation in `data/git/<feature>`, and a `@Binds @TabScope` entry in `app/di/modules/TabScopeGitActionsModule.kt`. ViewModels that the UI obtains directly must be exposed on `TabComponent` (assisted-inject ViewModels expose a `Factory`).

## CI

`.github/workflows/build_with_tests.yml` runs `./gradlew build` and `./gradlew test` on Ubuntu with JDK 25 for pushes/PRs to `main`. Release builds (`release.yml`) run on tags; fonts in `app/src/main/composeResources/font` are stored in Git LFS.
